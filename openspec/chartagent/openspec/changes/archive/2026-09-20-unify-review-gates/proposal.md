## Why

当前测量审核和生成图审核分别维护状态与流程。生成图审核已经在发布前执行，但测量审核主要依赖 `assemble_spec` 的最后一道引用校验，Agent loop 仍可能在审核未完成时处理同批次后续调用，前端也无法用统一方式表达“主链路已被审核阻塞”。这会让审核失败、修复中和未发布状态难以区分，并增加恢复时绕过审核的风险。

## What Changes

- 新增统一的审核协调器、审核尝试、审核决策、问题、修复动作和执行门禁模型。
- 将测量审核和生成图审核都纳入强制性的主链路门禁；审核未决、需要修复或失败时不得进入后续阶段。
- 测量审核失败后只允许执行有界的同面板定向重测；生成图审核失败后只允许基于诊断修正 ChartSpec 并生成新候选。
- 在同一批模型工具调用中，审核阻塞后停止尚未开始的后续调用，并保存带审核状态的 checkpoint。
- 保留测量审核和 VLM 图表审核各自的专业检查逻辑，仅共享生命周期、重试、证据引用、事件和门禁。
- 为普通运行与评测工作区提供统一的审核时间线、审核卡片、阻塞状态和修复下一步展示。
- 将审核不可恢复失败明确记录为非成功运行或非发布结果，禁止最终回答绕过门禁声称已完成或已发布。

## Capabilities

### New Capabilities

- `review-gates`: 为不同领域审核提供统一的有界生命周期、主链路门禁、修复循环、事件协议和前端投影。

### Modified Capabilities

- `measurement-quality-gate`: 测量质量审核成为 assemble 前的强制门禁，并在审核阻塞后停止无关工具调用。
- `vlm-chart-review`: 生成图审核接入统一门禁，审核中的候选不得继续发布或作为成功结果返回。
- `run-checkpoint-recovery`: checkpoint 必须保存活动审核门禁、审核尝试和受控修复动作，恢复不得绕过审核。
- `desktop-client`: 普通运行界面统一展示测量审核与生成图审核的状态、证据、问题和阻塞原因。
- `evaluation-workbench`: 评测只读界面复用统一审核展示，完整呈现审核事件、修复循环和最终门禁结果。

## Impact

- Python Agent loop、测量质量模块、ChartReviewManager、checkpoint/事件协议和 Gateway 运行摘要。
- React/Tauri 客户端的运行时间线、生成结果卡片、评测详情和协议类型。
- 需要新增共享审核状态与事件的持久化/恢复测试，以及测量失败、图表审核失败、超时、重连和同批调用截断测试。
- 不新增审核阶段的 OCR、CV 或测量工具调用；不改变测量审核与 VLM 审核各自的判断规则。
