## Context

后端已经使用统一的运行事件信封发布测量修复状态，修复上下文位于事件的受限 `repair` 字段中。Gateway 历史接口和 SSE 实时接口都返回 `runId`、`sequence`、`kind`、`timestamp`、`payload`，前端也已经有按 `runId:sequence` 合并事件的逻辑。

当前缺口在客户端接入层：Gateway 客户端的 SSE 事件白名单没有包含三个测量修复事件，运行时间线的中文标签也没有覆盖它们。因此历史回放和实时流可能表现不一致，实时修复事件甚至不会进入客户端。

## Goals / Non-Goals

**Goals:**

- 让三个测量修复事件进入实时 SSE 订阅，并沿用现有历史回放和重连机制。
- 在运行时间线中以中文、非成功语义展示修复请求、拒绝和耗尽状态。
- 用稳定的 run、sequence 和已有事件合并规则保证历史、实时、重连不重复。
- 仅展示有界、脱敏、允许展示的修复摘要，保留未知事件的安全回退。
- 用前端构建、smoke 和可重复的事件样例覆盖这条展示链路。

**Non-Goals:**

- 不改变后端 `measurement_repair_*` 事件的产生时机、状态机、字段名称或测量预算。
- 不在前端重新执行测量、审核、修复或发布，也不增加用户手动触发修复的操作。
- 不改变 Gateway 的持久化、事件序列分配、断点恢复和历史保留策略。
- 不把修复事件改造成新的终态；运行是否完成、失败或中断仍由运行生命周期事件决定。

## Decisions

### 1. 扩展现有事件订阅白名单，不增加新的传输通道

将三个事件类型加入现有 SSE 事件订阅集合，使其与模型、工具、审核和运行事件使用同一条传输路径。这样可以继续复用现有的 `afterSequence`、历史补齐和 `mergeEvents` 逻辑。

替代方案是新增一个专用的“测量修复”接口或前端轮询。该方案会产生第二套游标和状态同步问题，与执行追踪已有的统一事件模型冲突，因此不采用。

### 2. 保留通用事件信封，用窄化视图解释 repair 字段

不为每一种修复事件建立独立的传输协议；客户端继续消费通用 `AgentRunEvent`。在展示层增加一个受限的修复摘要解释，只读取 panel、attempt、parent attempt、target 类型、状态、原因和下一动作等允许字段，并对字符串和集合应用已有的文本边界。

这样既保持未知事件和未来字段的兼容性，又避免直接把原始 `repair` 对象或潜在敏感内容倾倒到用户界面。缺少字段时显示已有事件标签，不猜测数值或成功状态。

### 3. 标签表达生命周期状态，不表达业务成功

将 `measurement_repair_required` 映射为“需要定向重测”，将 `measurement_repair_rejected` 映射为“定向重测被拒绝”，将 `measurement_repair_exhausted` 映射为“定向重测次数已用尽”。这些事件保留在时间线中，但不改写运行终态、候选审核状态或发布状态。

替代方案是把修复请求显示成普通工具失败，或把耗尽直接显示成运行失败。前者丢失了“下一步仍由 Agent 决策”的语义，后者会把局部质量门禁和整个运行生命周期混为一谈，因此不采用。

### 4. 历史、实时和重连只维护一份事件集合

继续使用 `runId:sequence` 作为事件去重键，按 sequence 排序；修复事件不建立额外的前端状态副本。历史回放先到或实时事件先到都必须合并成同一条时间线，后来的同序事件不得重复渲染。

### 5. 用代表性修复事件补足前端验证样例

在 mock 或前端可复用的事件样例中覆盖 required、rejected、exhausted 三种状态，以及一次重复事件和一次未知事件。验证重点是“能订阅、能显示、能去重、能回退”，不把 mock 结果当作真实模型质量评估。

## Risks / Trade-offs

- **[后端字段新增或缺失]** → 展示层只读取允许字段，缺失时降级为稳定标签；未知字段不影响事件渲染。
- **[SSE 白名单遗漏导致实时事件不可见]** → 将三类事件加入同一集中列表，并在 smoke/build 检查中固定事件名称。
- **[历史回放与实时流重复]** → 复用现有 `runId:sequence` 合并逻辑，并增加 required 事件重复到达的验证样例。
- **[诊断内容泄露路径或敏感信息]** → 不直接渲染原始 repair 对象，只显示字段白名单和受限文本；详细敏感数据仍留在后端边界之外。
- **[用户误以为修复请求等于成功]** → 中文标签和状态样式明确区分“需要重测”“被拒绝”“次数用尽”，不改变运行终态。

## Migration Plan

这是向后兼容的前端增量变更，不需要数据迁移。前端先增加事件订阅和回退展示；旧 Gateway 不发送修复事件时，现有时间线行为保持不变。若需要回滚，只回退前端构建产物即可，已持久化的后端事件仍由历史接口保留。
